# Our Adventure — PRD v2 초안: 그룹 스탬프 투어

작성일: 2026-10-26 · 담당: 기획(Claude) · 상태: **2026-10-26 사용자 진행 승인**(디스코드 "진행해줘"). 구현 착수 가능, 출시 승인은 아님. 9장의 미결정 항목은 그대로 남는다.

v2는 [Phase 1 PRD v1.3](PHASE1_PRD.md)의 방향을 사용자의 2026-10-26 디스코드 결정으로 갱신한다.
충돌 시 이 문서가 우선한다. v1.3의 권한·실패 처리 원칙 중 아래에서 바꾸지 않은 것은 그대로 유지한다.

## 1. 한 줄 정의

**어디든 그룹이 함께 코스를 만들고, 장소마다 사진으로 스탬프를 모으고, 여행 후 결과 이미지로 남기는 서비스.**

가족 경주 MVP에서 아이가 좋아한 것은 Quest·스탬프를 모으는 재미였다. v2는 이 재미를 핵심 가치로 두고 그룹과 임의 여행지로 넓힌다.
외부 반복 사용·지불 의사는 아직 검증되지 않았다.

## 3. 핵심 사용자 흐름

1. **로그인** — 리더는 Google 로그인. 멤버는 4단계의 초대 링크와 별칭으로 참여(로그인 강요 없음).
2. **그룹 생성/선택** — 그룹명을 정해 만들거나 기존 그룹을 고른다.
3. **여행·코스 생성** — 여행명·날짜·방문 장소를 입력하면 장소별 스탬프가 자동으로 만들어진다. 리더가 이름·순서를 수정하고 확정한다.
4. **멤버 초대** — 링크로 초대. 한 번 그룹에 들어온 멤버는 다음 여행에도 그대로 참여한다.
5. **여행 중 기록** — 각 멤버가 장소에서 사진을 찍어 저장하면 **본인의** 해당 스탬프가 완료된다. 한 줄 느낌을 선택으로 붙일 수 있다.
6. **여행 후 결과** — 모든 멤버의 사진·스탬프를 모아 보고, 리더가 사진을 골라 리포트·인스타용 이미지를 만든다.

## 4. 기능 요구사항 (MVP)

### F1 로그인·그룹

- 리더는 Google 로그인 후 그룹을 만든다. 만든 사람이 그룹 리더다(그룹당 리더 1명).
- 리더는 자신이 속한 그룹 목록에서 기존 그룹으로 다시 들어간다.
- 정원은 그룹당 최대 10명(리더 포함). 30명은 후속 검증 목표다.

| ID | 수용 기준 |
|---|---|
| AC-1a | Google 인증 없이 그룹·여행 생성 요청 시 서버에서 거부 |
| AC-1b | 중복 클릭·응답 유실 시 그룹이 두 개 생기지 않음 |
| AC-1c | 재접속 시 같은 그룹·여행 목록이 보임 |

### F2 여행·코스·스탬프 생성

- 리더는 그룹 안에서 새 여행을 만든다: **목적지**, 여행명, 날짜(시작~종료), 방문 장소 목록.
- 새 여행은 **빈 상태로 시작**한다. 이전 여행의 장소·사진·스탬프를 가져오지 않는다(그룹 멤버만 이어짐).
- **목적지를 넣으면 추천 장소가 자동으로 채워진다**(2026-10-26 사용자 요청). 리더가 빼거나 직접 추가해 확정한다.
- **추천 방식은 하이브리드**(2026-10-26 사용자 확정):
  - 장소는 **지도 검색**으로 실제 존재하는 곳만 가져온다. 검색 결과가 없으면 직접 입력.
  - **AI는 그 장소의 미션·짧은 스토리만 작성**한다. 장소 자체를 AI가 만들지 않는다.
  - 미션은 사실 주장보다 **관찰형**(찾기·포즈·색깔·소리 등)으로 쓴다. 아이가 읽는 문장이므로 짧고 쉬운 말.
  - AI 결과는 **초안**이다. 리더가 확인·수정한 뒤 확정한다.
  - 리더당 생성 횟수를 제한한다(수치는 Engineering 제안).
  - AI 호출은 서버(Functions)에서 한다. 클라이언트에 API 키를 두지 않는다.
- 스탬프 상세 화면에 스토리와 "오늘의 미션"을 보여준다. 미션 수행 여부와 상관없이 사진을 남기면 완료된다.
- AI 입력·출력 형식·문장 규칙·금지사항은 [AI 코스 구성 가이드](AI_COURSE_GUIDE.md)를 따른다. 스탬프마다 **스탬프 이름·질문형 제목·관찰 미션·사진 아이디어**를 만든다(경주 앱 형식).
- 장소 1개 = 스탬프 1개. 스탬프는 **기본 디자인 템플릿**(아이콘 + 장소명)으로 자동 생성된다.
- 리더는 장소 이름·순서를 수정하고, 장소를 추가·삭제할 수 있다.
- 기존 경주 코스는 **준비된 코스 예시**로 제공해 바로 고를 수 있게 한다(코스 = 데이터, `courseId`).

| ID | 수용 기준 |
|---|---|
| AC-2a | 장소 N개 입력 시 스탬프 N개가 순서대로 생성 |
| AC-2e | 새 여행 생성 화면에 이전 여행의 장소·기록이 남아 있지 않음 |
| AC-2f | 목적지 입력 후 추천 장소가 채워지고, 추천이 없으면 직접 입력 안내 |
| AC-2g | AI 생성 중 로딩을 보여주고, 실패 시 장소는 유지한 채 미션 없이도 여행을 만들 수 있음 |
| AC-2h | AI가 만든 미션은 확정 전 리더가 수정할 수 있고, 지도 검색에 없던 장소를 AI가 추가하지 않음 |
| AC-2b | 장소가 0개인 여행도 만들 수 있고, 자유 기록만 가능 |
| AC-2c | 여행 진행 중 장소를 추가하면 모든 멤버의 스탬프판에 반영, 이미 완료된 스탬프는 유지 |
| AC-2d | 사진이 남은 장소의 삭제는 영향 안내 후 확인 받음 |

### F3 멤버 초대·참여

- 리더가 그룹 초대 링크를 공유한다. 멤버는 링크 → 그룹 소개 → 별칭 입력 → 참여.
- 그룹 멤버는 그룹 안의 모든 여행에 자동으로 참여한다.
- 별칭은 표시용이며 권한 근거가 아니다. 다른 기기·브라우저 데이터 삭제 시 복구를 약속하지 않는다(안내 표시).

| ID | 수용 기준 |
|---|---|
| AC-3a | 9명 상태에서 2명이 동시에 참여해도 최종 10명, 초과는 명확히 거부 |
| AC-3b | 같은 사람이 링크를 다시 열어도 멤버가 중복되지 않음 |
| AC-3c | 잘못된 링크·정원 초과는 구분해 안내하고 그룹 내용을 노출하지 않음 |

### F4 사진으로 개인 스탬프 완료

- 멤버가 스탬프를 열고 사진을 찍거나 고르면, 사진이 저장된 뒤 **본인의** 스탬프가 완료된다.
- 한 줄 느낌(선택)을 사진과 함께 남길 수 있다.
- 같은 스탬프에 사진을 다시 올리면 사진이 추가되고, 완료 상태는 유지된다.
- 스탬프판은 본인 진행을 기본으로 보여주고, 그룹 화면에서 멤버별 진행(예: 아이 5/9, 엄마 7/9)을 함께 보여준다.
- 위치(GPS) 확인은 MVP에서 하지 않는다. 사진만 있으면 완료한다.

| ID | 수용 기준 |
|---|---|
| AC-4a | 사진 업로드와 기록 저장이 모두 성공해야 '완료'. 실패 시 입력 보존·재시도 |
| AC-4b | A의 완료가 B의 스탬프에 영향을 주지 않음 |
| AC-4c | 중복 클릭·재시도로 같은 사진이 두 번 저장되지 않음 |
| AC-4d | 다른 기기에서 다시 열어도 같은 완료 상태(같은 계정·세션 기준) |
| AC-4e | 완료 식별 기준은 그룹·여행·장소·인증된 참여자. 별칭은 식별 근거로 쓰지 않고, 다른 여행의 완료가 섞이지 않음 |
| AC-4f | 한 줄 느낌 없이 사진만 저장해도 완료 |

### F5 함께 보기·자유 기록

- 여행 안의 모든 멤버 사진·한 줄 느낌을 최신순 피드와 장소별 모음으로 본다.
- 장소와 무관한 **자유 기록**(사진 + 한 줄)도 남길 수 있다. 스탬프에는 반영되지 않는다.
- 본인 기록만 수정·삭제할 수 있다. 리더도 타인 기록은 수정·삭제하지 않는다.
- 본인 스탬프 사진을 모두 삭제하면 해당 스탬프는 미완료로 돌아간다.

| ID | 수용 기준 |
|---|---|
| AC-5a | 그룹 비멤버는 주소·ID를 알아도 사진·기록을 볼 수 없음 |
| AC-5b | 업로드 중인 사진은 다른 멤버에게 보이지 않음 |
| AC-5c | 타인 기록 수정·삭제 요청은 서버에서 거부 |

### F6 여행 후 결과물

- 리더가 여행을 **종료**하면 결과 화면이 열린다. 종료 후 새 기록은 막고, 열람은 유지한다.
- **여행 리포트**(앱 화면): 기간, 장소 수, 멤버별 스탬프 달성, 장소별 대표 사진, 한 줄 느낌 모음.
- **인스타용 이미지**: 리더가 사진을 골라 템플릿에 넣고 PNG로 저장한다.
  - 피드 1080×1350, 스토리 1080×1920
  - MVP 템플릿 2~3종(예: 스탬프 모음판, 사진 그리드 + 한 줄, 장소별 하이라이트)
- 멤버도 리포트를 보고, 본인 스탬프판 이미지를 저장할 수 있다(후속 확인).
- 기존 A4 일기·앨범 출력은 후속으로 둔다.

| ID | 수용 기준 |
|---|---|
| AC-6a | 비리더의 종료·결과 구성 요청은 서버에서 거부 |
| AC-6b | 0장 선택·사진 로딩 실패 시 빈 이미지를 저장하지 않고 안내 |
| AC-6c | 모바일(iOS Safari, Android Chrome)에서 PNG 저장 동작 확인 |
| AC-6d | 미리보기와 저장된 이미지의 배치·글자가 일치 |

### F7 여행 화면 구성·지난 여행 열람 (2026-10-26 사용자 요청)

- 여행 안의 하단 탭은 기존 경주 앱과 같은 **지도 · 코스 · 스탬프 · 추억** 4개다(리더·멤버 공통).
  - 지도: 장소 핀과 경로, 본인 완료 표시, "다음 탐험" 바로가기.
  - 코스: 장소 순서와 장소별 스토리·미션.
  - 스탬프: 본인 스탬프판과 멤버별 진행.
  - 추억: 함께 남긴 기록 피드, 자유 기록, 종료 후 리포트·결과 이미지 진입.
- 리더에게만 상단 **여행 관리**(초대 링크·참여 현황·종료)를 보여준다.
- 그룹 화면의 여행 목록에서 **종료된 여행도 열어** 지도·코스·스탬프·추억과 리포트를 볼 수 있다. 쓰기는 막는다.

| ID | 수용 기준 |
|---|---|
| AC-7a | 종료된 여행을 열면 같은 4탭과 리포트가 보이고, 사진·스탬프 작성 버튼은 보이지 않음 |
| AC-7b | 새 여행을 만들어도 지난 여행 기록이 그대로 남아 목록에서 열림 |

## 6. 데이터 구조 방향 (Engineering 확정 대상)

```
Group (리더, 멤버[], 초대 링크)
 └─ Trip (여행명, 기간, 상태: 준비→진행 중→종료, courseId?)
     ├─ Place/Stamp (순서, 이름, 아이콘)
     ├─ StampCompletion (멤버, Place, 완료 시각)   ← 개인별
     └─ Post (멤버, Place? , 사진[], 한 줄)       ← Place 없으면 자유 기록
```

- PR #3의 인증·참여·`course.json` 구조를 재사용하고, 그룹 ⊃ 여행 계층과 개인 스탬프로 바꾼다.
- 기존 루트 앱(`index.html`)과 로컬 저장 데이터는 그대로 보존한다(v1.3 FR-10 유지).

## 7. MVP 제외 (후속)

## 10. 역할과 진행 방식 (2026-10-26 사용자 확정)

사용자 결정: **기획부터 목업까지는 Claude, 이미지를 포함한 개발 구현은 Codex.** 양쪽이 같은 일을 하지 않는다.

| 단계 | 담당 | 산출물 |
|---|---|---|
| 기획 (PM · Product Strategy) | Claude | PRD, 화면 흐름, 수용 기준, 결정 기록 |
| 목업 | Claude | 눌러볼 수 있는 화면 목업 ([v2 목업](https://claude.ai/artifact/55N2ouuNnoAtBgRrXJ7XBZ)) |
| 구현 (이미지 · Designer · Engineer) | Codex | 실제 이미지·스탬프·결과 템플릿 에셋, 앱 구현, 실행 방법 |
| QA | Claude 기준 작성 → Codex 실행·결과 보고 | 체크리스트, 실기기 결과 |

**의사결정 구조 (2026-10-26 사용자 승인)**

| 역할 | 담당 | 책임 |
|---|---|---|
| 오너 | 사용자 | 방향·예산·출시·머지 승인 |
| PM | Claude | PRD·목업, 우선순위, 작업 순서([MVP 작업 목록](MVP_TICKETS.md)), 결정 기록, 진행 현황 |
| 테크 리드 | Codex | 기술 방식·견적·구현·테스트, 기술 리스크 제기 |

- 구현 착수는 PRD·목업 승인 후. 승인 전 코드는 "기술 검증(스파이크)"으로 표시한다.
- PRD는 PM만 수정한다. 구현 중 차이는 Codex가 PM에게 전달한다.
- 작업은 티켓 1개 = PR 1개를 기본으로 하고, 머지는 사용자가 승인한다.
- 기획·목업 질문은 Claude, 이미지·구현 질문은 Codex를 멘션한다.
- Claude는 PRD·목업을 고치고, Codex는 PRD 문서를 직접 고치지 않고 구현 중 발견한 차이를 Claude에게 넘긴다.
- 공통 기준은 이 저장소다. ChatGPT 스레드의 결정 사항은 `docs/`로 옮긴다.
- 순서: PRD v2·목업 승인 → Codex가 이미지·개발 착수(PR #3 재사용) → QA → 파일럿.
