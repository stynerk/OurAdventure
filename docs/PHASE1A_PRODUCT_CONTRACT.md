# Phase 1A — 공동 기록 제품 계약 초안

작성: 2026-10-20. 담당: Product Strategy. 상태: **검토 초안 / 구현·출시 승인 아님**.

기준: [PRD v1.1 0절](PHASE1_SHARED_ADVENTURE_SPEC.md). 기존 승인 범위와 이 문서의 신규 권고를 구분한다. Firebase 콘솔 세팅 진행은 저장소·요금제·보관·권한 정책 승인으로 해석하지 않는다. 기술 구현 및 실측은 Engineering/QA가 별도 수행한다.

## 1. 상태 정의 및 범위

| 표시 | 의미 | 사용 방법 |
|---|---|---|
| 승인됨 | PRD v1.1에 기록된 사용자 결정 | 구현 범위의 기준 |
| 권고 기본값 | 작은 가족 파일럿용 Product 제안 | 목업·설계에 사용 가능하나 출시 정책 확정 아님 |
| 사용자 결정 필요 | 비용·보관·접근·삭제 등 외부 사용 약속 | 선택지와 영향을 제시하고 확정 기록 후 외부 운영 |

| 항목 | 계약 | 상태 |
|---|---|---|
| 대상 | 리더 포함 최대10명, 리더1명, 활동 공간당 여행·활동1건 | 승인됨 |
| 핵심 흐름 | 초대 → 구성원 글·사진·활동 기록 → 함께 보기 → 리더 선택·정렬 → 일기/앨범 출력 | 승인됨 |
| 인증 | 리더 Google / 구성원 로그인 UI 없이 내부 익명 인증, 방별 멤버십 | 승인됨 |
| 기존 자산 | 루트 앱과 `gj-family-quest`, `gj-family-diary-template` 보존; 자동 사진 업로드·이전 없음 | 승인됨 |
| 후속 단계 | 30명은1B 테스트, 개인 제출·학교 보고서는1C, 코스 제작은 Phase2 | 승인됨 |
| 저장 방식 | 신규 사진은 구성원 간 공유 가능해야 함. 공급자·요금제·기술 경로 미확정 | 사용자 결정 필요 / Engineering 제안 필요 |

1A는 공동 모드부터 제공한다. 게시글과 스탬프는 연결할 수 있지만 서로를 필수 조건으로 만들지 않는다. 사진 없는 Quest 완료를 보존한다. 게시글을 삭제해도 공동 스탬프를 취소하지 않는 것을 권고한다.

## 2. 기록 입력·게시·수정 계약

아래 수치와 상세 동작은 모두 **권고 기본값**이다. 공개 약속·서버 제한으로 적용하기 전에 결정 로그에 확정한다.

| 항목 | 권고 기본값 | 이유 / 경계 |
|---|---|---|
| 입력 | 본문0~500자 + 사진0~1장 + 기존 Quest 선택 연결 | 짧은 현장 입력·기존 A4 재사용 |
| 최소 내용 | 공백 제거 후 본문 또는 처리 가능한 사진 중 하나 필수 | 빈 글 방지; 사진 단독·글 단독 허용 |
| 작성자 | 인증 uid와 방 멤버십으로 고정, 별칭은 표시용 | 동일 별칭을 같은 사람으로 취급하지 않음 |
| 시각 | 게시·수정 시각은 서버 기준, 단말 촬영시각은 정렬 기준 아님 | 시계차·중복·개인정보 노출 방지 |
| 게시판 순서 | 서버 게시시각 최신순, 같은 시각은 안정적 ID 순서 | 새로고침 시 임의 재정렬 방지 |
| 사진 | 게시 전 미리보기·교체·취소, 원본 기기는 변경하지 않음 | 사용자가 공유 대상을 확인 |
| 초안 | 우선 화면 내 임시 초안; 서버 저장 성공 전 공개되지 않음 | 영구 초안·오프라인 큐는1A 필수 제외 |
| 편집 | open 상태에서 작성자만 본문·사진·Quest 연결 수정 | 리더가 타인 경험을 대신 고치지 않음 |
| 충돌 | 최신 버전 검사 후 충돌 안내·재확인; 무음 덮어쓰기 금지 | 두 탭·재시도에서도 기록 신뢰 유지 |

게시 전 “이 활동의 구성원에게 공유됩니다. 리더가 일기·앨범에 포함할 수 있습니다.”를 안내한다. Google 이메일·실명·위치·원본 EXIF를 게시글에 자동 첨부하지 않는 것을 권고한다. 파일 메타데이터 제거의 기술 보장은 Engineering이 검증한다.

### 게시 성공과 실패

- 사진이 있는 글은 사진 준비와 게시 메타데이터의 서버 확정이 모두 끝나야 `게시됨`이다. 업로드 성공만으로 게시 성공을 표시하지 않는다.
- 게시 중 버튼 중복 입력과 응답 유실 후 재시도는 같은 요청 ID로 재사용하며 게시글·사진 중복을 만들지 않는다.
- 네트워크 실패 시 작성 내용을 화면에 보존하고 `게시 실패·다시 시도`를 제공한다. 다른 기기에서는 미완성 글을 공개하지 않는다.
- 사진 오류 시 글만 자동 게시하지 않는다. 사용자가 `사진 없이 게시`를 명시 선택할 때만 별도 게시한다.
- 도중 방 종료·인원 권한 상실·한도 도달은 성공으로 표시하지 않는다. 화면 초안은 복사·저장할 기회를 제공한다.
- 첨부 변경 실패 시 기존 게시물·기존 사진을 유지한다. 새 사진 확정 전 이전 사진을 제거하지 않는다.
- 고아 업로드·대기 파일의 정리와 용량 계산은 서버 처리 계약이 필요하다. 공급자별 정리 작업 방식은 이 문서에서 확정하지 않는다.

## 3. 권한 계약 제안

아래 상세 권한은 **권고 기본값**이며 PRD의 미결정 열람·삭제 정책을 대체 승인하지 않는다. UI 숨김과 별도로 서버·저장소가 같은 규칙을 강제해야 한다.

| 동작 | 비구성원 / 링크만 소유 | 구성원 | 리더 |
|---|---|---|---|
| 입장 전 정보 | 활동 이름·코스·종료/정원 상태만 최소 노출 | 해당 없음 | 관리 정보 확인 |
| 게시판·사진 열람 | 불가 | 해당 방의 공개 완료 글만 | 해당 방의 공개 완료 글만 |
| 새 글 게시 | 불가 | open에서 가능 | open에서 가능 |
| 타인 글 수정 | 불가 | 불가 | 불가 |
| 본인 글 수정 | 불가 | open에서 가능 | open에서 가능 |
| 본인 글 삭제 | 불가 | open에서 확인 후 가능 | open에서 확인 후 가능 |
| 타인 글 삭제/숨김 | 불가 | 불가 | 정책 결정 전 일반 UI 제공 안 함 |
| 출력 구성 선택·정렬 | 불가 | 불가 | 가능; 원본 글 변경 아님 |
| 활동 종료 | 불가 | 불가 | 가능 |

출력 기능의 제품 주체는 리더다. 구성원이 이미 열람한 사진의 저장·스크린샷을 기술적으로 완전히 막는다고 약속하지 않는다. 초대 토큰·파일 URL 자체가 관리자 권한이나 영구 공개 권한이 되어서는 안 된다. 다른 방 member와 비구성원은 객체 ID·첨부 주소를 알아도 신규 요청이 거부되어야 한다. 구현 수단은 Engineering이 제안한다.

삭제 후에는 게시판·새 출력에서 즉시 제외하고, 원본 파일의 물리 삭제·캐시·복구 범위는 별도로 안내한다. `숨김`을 `영구 삭제 완료`로 표시하지 않는다. 이미 내려받은 PNG·인쇄물·기기 복사본은 회수할 수 없음을 명시한다.

## 4. 종료 후 행동 및 리더 출력

| 상태·동작 | 제안 | 상태 |
|---|---|---|
| 종료 | 리더만 종료, Quest 진행은 읽기 전용, 재오픈 없음 | 승인된 기존 규칙 |
| 종료 확인 | 새 참여·새 글·수정이 중단된다는 영향 안내 | 권고 기본값 |
| 종료된 게시판 | 기존 구성원 열람 가능, 신규 가입·새 글·일반 편집 중지 | 권고 기본값 |
| 종료 후 삭제 | 일반 편집과 별개 삭제 요청 경로 필요; 처리 주체·기한 확정 전 영구 보관 약속 금지 | 사용자 결정 필요 |
| 출력 가능 시점 | open/closed 모두 리더가 선택·정렬·재출력 | 권고 기본값 |
| 출력 구성 | 앨범/일기, 초기에 A4 한 장당 최대9개 기록 선택; 초과는 안내 | 권고 기본값 |
| 미리보기 | 선택 사진·본문·별칭·순서를 실제 출력과 동일하게 확인 | 권고 기본값 |
| 잘림·누락 | 수용 불가한 긴 글은 입력/선택 조정 안내, 무음 누락 금지 | 권고 기본값 |
| 삭제·변경과 출력 | 출력 직전 최신 원본·권한을 재검증; 삭제·수정 감지 시 재미리보기 | 권고 기본값 |

출력 구성은 원본 글의 공개 범위·본문·사진을 바꾸지 않는다. 제목·순서·선택을 편집하는 경험만 우선한다. 기록이 0개면 생성 CTA를 비활성화하고 기록 추가를 안내한다. 초기 다중 페이지·PDF·AI 요약은 확정하지 않는다. 사용자가 다운로드한 파일과 서버에 남은 원본은 구분한다.

## 5. 용량·보관·비용 선택안

다음은 **견적·설계용 제안**이다. 서버 설정·보관 약관·지원 보장이 아니다.

| 항목 | 권고하는 파일럿 초기값 | 결정할 사항 |
|---|---|---|
| 게시글 수 | 방당100개, 1글1사진; 수정·삭제 시 사용량 재계산 | 실제 촬영량과 입력 불편 검증 후 조정 |
| 이미지 처리 | 장변1600px 이하 재인코딩, 저장본1MiB 이하 목표·초과 거절, 원본 장기보관 안 함 | HEIC 등 입력 형식·압축 품질·보안 검사 |
| 방당 사진 | 확정된 저장본 합계 최대100MiB | 대기 업로드 예약량 포함 원자적 제한 필요 |
| 업로드 빈도 | 중복 방지 외 별도 남용 방지 필요 | 요청 빈도·동시 업로드 제한은 Engineering 제안 |
| 보관 | 종료 후90일 읽기/출력 제공을 비교안으로 검토 | 자동삭제 여부·사전 알림·삭제 실행/복구 유예·지원 범위 |
| 비용 | 방 단위 사용량과 전체 계정 예산을 함께 측정 | 사용자 월 예산, 과금 계정/요금제, 초과 시 행동 |

100MiB는 방의 사진 저장본 상한 제안이다. 임시 파일·썸네일·메타데이터·트래픽·출력 생성·백업 비용을 포함하지 않는다. 따라서 방당 비용이나 전체 서비스 수용량을 보장하지 않는다. 사용량 제한 실패 시 정상 이용자 데이터가 삭제되는 방식으로 예산을 맞추지 않는다.

| 사용자 결정 필요 | 권고안과 대안 | 트레이드오프 |
|---|---|---|
| 열람·리더 관리 | 구성원 전원 열람 + 작성자 편집/삭제를 권고. 대안: 리더 승인 게시·숨김 허용 | 단순 현장 경험 vs 통제·운영 부담 |
| 종료 뒤 삭제 | 삭제 요청 접수와 처리 주체를 정하는 안 권고. 대안: 종료 뒤 작성자 삭제 허용 | 출력 안정성 vs 개인 통제·즉시성 |
| 보관·삭제 | 종료 후90일 비교안. 대안:30일/수동 기간 연장 | 다시 출력할 시간 vs 비용·운영 부담 |
| 이미지·방 한도 | 위100개/100MiB 제안. 대안: 더 낮은 파일럿 제한 또는 상향 | 사진 선택 부담 vs 비용·성능 |
| 비용·저장소 | Engineering 견적과 실제 파일럿 사용량 후 선택 | Firebase 콘솔 개설 자체는 저장 서비스·유료 요금제 승인 아님 |

보관 정책 미확정 동안 예약 자동삭제 작업을 가동하거나 “영구 보관”을 약속하지 않는다. 외부 파일럿에 앞서 알림 채널을 어떻게 확보할지도 결정한다. 익명 참여자에게 이메일 알림을 보낼 수 있다고 가정하지 않는다. 단순 콘솔·목업 개발은 이 결정과 독립적으로 진행할 수 있다.

## 6. 수용 기준 초안

각 항목은 위 권고가 채택됐을 때의 검증 계약이다. 실제 구현·통과·지원 승인을 뜻하지 않는다.

| ID | Given / When | Then |
|---|---|---|
| AC-01 | 리더 포함9명인 방에 독립된2세션이 동시에 입장 | 최종 멤버 최대10명, 한 요청만 성공, 거절 세션에 원인 안내 |
| AC-02 | 같은 uid가 같은 입장 요청 재시도 | 멤버 중복·정원 중복 차감 없음 |
| AC-03 | 공백만 입력·사진 없음 / 글만 / 사진만 게시 | 빈 글 거절, 글·사진 단독은 각각 허용 |
| AC-04 | 같은 별칭 두 사람이 글 게시 후 수정 시도 | uid별 소유권 분리, 타인 글 변경 거부 |
| AC-05 | 사진 업로드 완료 후 게시 저장 실패·응답 유실·재시도 | 미완성 글 공개 안 됨, 성공 중복글 없음, 초안 유지 |
| AC-06 | 기존 사진 교체 중 실패 | 이전 글·사진 열람 유지, 실패를 성공으로 안내하지 않음 |
| AC-07 | 비구성원·다른 방 member가 게시글/사진 주소 요청 | 서버·객체 저장소 양쪽에서 거부, 관리 권한 상승 불가 |
| AC-08 | 리더가 타인 글 수정 또는 구성원이 타인 삭제 요청 | 권한 거부; 리더 출력 순서 변경은 원본에 영향 없음 |
| AC-09 | 게시와 방 종료가 경합 | 종료 후 새 게시 확정 차단, 작성자에게 결과/초안 안내 |

## 7. 핸드오프 및 출시 전 결정

- Product: 권고안과 사용자 결정 결과를 구분해 PRD/결정 로그에 반영. 게시판 구조·출력 경험을 가족 테스트로 확인.
- UX: 작성·실패·충돌·삭제·종료·한도·미리보기 상태 설계. 익명 세션 소실 시 복구 보장 없음 안내.
- Engineering: Firebase 세팅과 독립해 저장 공급자/접근제어/원자적 한도/재시도/삭제 실행·비용 추정 제안. 고정 수치의 설정화 검토.
- QA: AC별 서버 거부·실제 사진·독립 세션·모바일 출력 증거 기록. 30명 테스트 통과를10명 출시 QA와 구분.

외부 파일럿 전에는 열람·삭제·종료 후 처리, 저장/보관·비용 한도, 실패 및 권한 검증 결과를 확정한다. 이 문서 생성은 해당 결정을 대신하지 않는다.
