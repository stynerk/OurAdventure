# Discord 협업 자동화 진단·제안 — 2026-10-28

요청: 사용자가 매번 업무를 다시 지정하지 않고 PM과 개발 담당 사이에 인계·검토·재작업이 이어지게 한다. 이 문서는 확인한 사실과 구현 제안을 구분한다. 봇 설정 변경이나 자동 실행 설치를 완료했다는 뜻이 아니다.

## 확인한 범위

- 프로젝트의 `.github/workflows/test.yml`은 push/PR 검증, `pages.yml`은 사이트 배포다. 저장소 안에서 PM 작업 준비 → 개발 실행 → PM 검토를 전달하는 dispatcher/대기열/재개 작업은 확인되지 않았다.
- `docs/HANDOFF.md`의 인수 확인 절은 역할별 대화 스레드가 자동 동기화된 것이 아니라고 명시한다. R&R·PRD를 공유하는 것과 상대 담당 실행을 시작하는 것은 별도다.
- 이번 개발 세션에는 Discord 메시지 조회·송신·예약 실행 도구가 제공되지 않았다. 저장소/PR은 확인할 수 있었지만 PM 봇의 채널 메시지 전체를 읽고 수신 확인을 보내는 연결은 검증할 수 없었다.
- 지정 작업공간에는 Orca Discord relay의 실행 소스·수신 로그·실제 봇 설정이 없다. 다른 계정/프로필/프로젝트를 열어 추측하지 않았다. 봇 메시지 무시, 멘션 전용 실행, 역할 멘션 전달 실패 중 어느 것이 실제 설정인지는 아직 확인되지 않았다.

따라서 확인한 사실은 **프로젝트에서 R&R을 공유하고 있지만 역할 간 작업 전달과 다음 담당 실행을 보장하는 연결은 검증되지 않았다는 점**이다. 사용자의 업무 메시지가 실행 트리거를 대신하고 있는 것이 가장 유력한 설명이다. 외부 Orca 릴레이의 설정·로그를 보지 못했으므로 전체 시스템의 연결 부재나 특정 봇의 장애로 확정하지 않는다.

## Discord에서 확인할 항목

Discord 메시지는 사람과 봇이 모두 작성할 수 있다([공식 Message 구조](https://github.com/discord/discord-api-docs/blob/main/developers/resources/message.mdx)). `MESSAGE_CONTENT`는 콘텐츠 수신과 관련된 intent이며, 설정만으로 개발 작업이 시작되는 것은 아니다([공식 Gateway 문서](https://github.com/discord/discord-api-docs/blob/main/developers/events/gateway.mdx)).

릴레이 진단 시 같은 작업에 대해 `수신 → 필터 통과 → 담당 선택 → 실행 시작 → ACK` 5단계의 event_id 로그를 확인한다. `author.bot`/webhook 일괄 무시 여부, 직접 멘션과 역할 멘션의 분기, 허용 채널·봇 ID, MESSAGE_CONTENT가 필요한 수신 방식인지, 중지 상태·작업 중 잠금·세션 종료 후 재개 여부를 각각 확인해야 한다. 토큰 값을 채널에 공유할 필요는 없다.

## 권장 구조

GitHub Issue를 작업 원장으로 두고, 중계 실행기 하나가 상태 변화를 전달한다. Discord는 사람에게 진행·이슈를 알리고 필요한 결정을 받는 창구로 유지한다.

1. PM이 승인 범위·AC·기반 PR이 갖춰진 티켓을 READY로 설정한다. 중계기가 DEV 작업을 큐에 넣고 실제 실행기의 수신 확인을 받는다.
2. 개발 담당이 구현·테스트 후 Draft PR과 증거를 남기면 REVIEW로 바뀌고 PM 검토 실행을 요청한다.
3. PM의 검토가 CHANGES_REQUESTED이면 같은 브랜치로 개발 재작업을 전달한다. 새 티켓/중복 PR을 만들지 않는다.
4. 검토·CI 통과 시 OWNER_REVIEW로 넘기고 사용자에게 요약을 알린다. 승인된 범위의 개발·테스트·Draft PR은 매번 사용자 지시를 다시 요구하지 않는다. 머지·배포·과금·접근 권한 변경은 기존 사용자 승인 경계를 유지한다.

일반 봇 대화를 전부 작업으로 실행하지 않는다. 사용자가 원한 '다른 봇 멘션에는 불필요하게 답하지 않기'는 유지하고, 지정 PM이 보내는 TASK_READY/REVIEW_CHANGES 같은 명시적 인계 이벤트만 개발 실행으로 취급한다. 필요하면 Issue 상태 변경을 정본 이벤트로 사용해 봇 간 채팅 필터에 의존하지 않는다.

이벤트 최소 필드: event_id, task_id, spec_revision, event_type, from_role, to_role, base_pr, head_sha, expected_state. 인증된 송신자·지정 채널/저장소만 허용한다. event/task/revision으로 중복을 막고 한 작업의 개발 실행은 하나만 점유한다. 실행 중 새 검토는 다음 작업으로 보관하며, ACK 누락·실패는 제한된 재시도 후 이유를 보고한다. 중지 상태는 큐와 재시작 후에도 유지한다. 자기 메시지·일반 보고에는 응답을 연쇄 생성하지 않는다.

## 구현 순서와 완료 기준

첫 단계는 Orca의 해당 Discord 릴레이 소스/설정이 제공된 작업공간에서 위 5단계 로그를 확인하는 것이다. 다음은 GitHub 이벤트 → 큐 → 실제 개발/PM 실행 어댑터 → Discord 요약의 최소 연결이다. 지원되지 않는 비공개 API가 있다고 가정하지 않는다. 전용 채널에서 실제로 실행기를 깨울 수 있는 연결이 확인돼야 한다.

완료 기준: 사용자는 범위 승인 한 번만 한다. PM READY 이후 사람이 메시지를 복사하지 않아도 개발 Draft PR → PM 검토 → 수정 1회 → 최종 보고까지 이어져야 한다. 같은 이벤트 재전송은 중복 PR을 만들지 않고, 무관한 봇 메시지는 실행하지 않으며, stop 후 새 실행이 생기지 않아야 한다. 실행기 재시작 후 대기 작업도 유실되지 않아야 한다.

현재 구현 상태: 진단·제안만 작성. 실 봇 간 인계·예약·수신 정책·권한은 변경하지 않았다.
