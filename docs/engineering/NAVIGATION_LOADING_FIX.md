# 로그인·생성 후 로딩 중단 후속 — 2026-10-30

사용자 보고: 로그인, 새 여행 등록, 코스 생성 뒤 로딩이 끝나지 않고 새로고침해야 다음 화면이 보인다.

## 확인 범위와 변경

기존 운영 검사는 비로그인 첫 화면·설정·GA 전송과 인증 거부 요청 중심이었다. 기존 그룹 브라우저 검사는 Google 자격 증명을 SDK에 직접 주입해 로그인 버튼의 팝업 흐름을 거치지 않았다. 실제 사용자의 Google OAuth와 특정 기기에서 같은 현상이 발생하는 조건을 확인한 것으로 표시하지 않는다.

운영의 임시 익명 인증 → 그룹 목록 및 목록 재조회 3회는 새로고침 없이 통과했다. 여행·사진 데이터는 만들지 않았고, 임시 인증 계정은 검사 후 삭제했다. 코드에서는 Firestore 서버 읽기에 앱 수준 종료 시간이 없어 요청이 정체되면 경로 전체가 로딩 상태에 머물 수 있음을 확인했다.

- Firestore 초기화를 유한 응답의 long polling 방식으로 바꿨다. 스트림을 버퍼링하는 브라우저/프록시와의 호환성을 우선하며 네트워크 요청 수가 늘 수 있다. 이 설정만으로 보고자의 기기 원인이 확정됐다고 주장하지 않는다.
- 문서·목록 읽기는 12초 내 응답이 없거나 unavailable이면 연결을 재설정하고 한 번 재시도한다. 동시에 멈춘 읽기는 진행 중인 복구를 공유한다. 재시도도 실패하면 기존 오류 화면과 ‘다시 확인’ 버튼을 제공한다. 권한 거부는 재시도하지 않는다.
- callable 제한 시간은 서버의 30초보다 긴 35초로 명시했다. 생성·업로드를 자동으로 재전송하지 않으며 기존 요청 ID·입력 보존 절차를 유지한다.
- 서버·보안 규칙·데이터 모델과 기존 여행 기록은 변경하지 않았다.

## 회귀 검사

`npm test`: 47개 통과. 신규 단위 검사는 무응답 읽기 복구, 동시 복구 공유, 권한 오류 비재시도, 지속적인 읽기/복구 지연의 유한 종료를 확인한다.

`npm run test:navigation`: 실제 Auth 에뮬레이터 Google 팝업을 로그인 버튼으로 열고 합성 계정을 선택한다. 팝업 로그인 → 그룹 → 여행 → 코스 → 장소 추가가 상위 문서 요청 1회로 이어지는지 검사한다. 이후 Firestore 응답을 고의로 보류해 무한 로딩 대신 오류 화면이 나오며, 연결 복구 후 ‘다시 확인’이 새로고침 없이 성공하는지 확인한다. 이 검사도 CI에서 Chromium 설치 후 실행한다.

새 브라우저 검사는 에뮬레이터 범위다. 실제 Google 계정 팝업과 사용자 기기의 같은 네트워크 조건은 배포 후 사용자 확인이 필요하다. Chrome 검사를 물리 iPhone/Android 검증으로 표시하지 않는다.

관련 근거: [Firebase Firestore 연결 설정](https://firebase.google.com/docs/reference/js/firestore.firestoresettings). 기존 SDK에 long polling 자동 감지는 기본 활성 상태였으므로 자동 감지를 새로 켰다고 설명하지 않는다.
